# خطة تنفيذ تطبيق ملاحة للعراق

هذه الخطة تجمع بين متطلبات المنتج والتصميم الواردة في ملف `iraq_navigation_app_design.md` مع تصور تنفيذي قابل للتطوير.

## 1. نطاق الـ MVP
- **الخرائط والملاحة:** عرض خريطة حية، توجيه خطوة بخطوة، إعادة توجيه تلقائية عند الخروج عن المسار.
- **البحث:** اقتراحات سياقية (منزل/عمل)، دعم الصوت بالعربية/الكردية، وإكمال تلقائي لنقاط الاهتمام المحلية.
- **التنبيهات المجتمعية:** إرسال/استقبال بلاغات (حادث، زحام، نقطة تفتيش، طريق مغلق، مطر)، مع تصويت لتأكيد الموثوقية.
- **الوضع الليلي والوضع الاقتصادي:** تقليل السطوع، خفض استهلاك البيانات عبر تحديثات أقل وتخزين بلاطات مؤقتة.
- **اللغات:** واجهة عربية وكردية مع RTL افتراضي، وإمكانية التبديل الفوري.

## 2. البنية التقنية المقترحة
- **العمارة العامة:**
  - **تطبيقات العملاء:** Kotlin Multiplatform (Android/iOS) أو Flutter إذا تفضّل فرق الواجهة الموحدة.
  - **خدمة الملاحة:** محرك مسارات (OSRM/GraphHopper) مع طبقة تحسين لحركة المرور الحية.
  - **واجهة برمجة التطبيقات:** REST/GraphQL لإدارة الحسابات، المفضلة، التنبيهات، والرحلات.
  - **البيانات المكانية:** OpenStreetMap + تحسينات محلية، مع تخزين بلاطات MBTiles للاستخدام دون اتصال.
  - **الحوسبة الفورية:** Kafka أو Pub/Sub لتدفق بلاغات المجتمع وتحديثات الحركة، مع استهلاك فوري لتعديل التوجيه.
  - **المراقبة:** Prometheus + Grafana، وأتمتة تنبيهات عبر Alertmanager، مع Crashlytics/Sentry على التطبيقات.

## 3. نموذج البيانات المبدئي
- **المستخدم:** `id`, `phone`, `display_name`, `preferred_language`, `vehicle_type`, `home_location`, `work_location`.
- **المفضلة/الوجهات:** `id`, `user_id`, `label` (منزل/عمل/مخصص), `location (lat,lng)`, `notes`.
- **التنبيهات المجتمعية:** `id`, `user_id`, `type` (accident/traffic/checkpoint/closure/weather/pothole), `location`, `radius`, `severity`, `status` (open/confirmed/invalid), `expires_at`.
- **الرحلة الحية:** `trip_id`, `user_id`, `origin`, `destination`, `waypoints[]`, `eta`, `current_progress`, `share_url`.
- **إعدادات التطبيق:** `language`, `theme`, `data_saver`, `voice_pack`.

## 4. واجهات برمجة التطبيقات الأساسية
انظر ملف `backend_api.md` للتفاصيل؛ أهمها:
- إدارة الحساب والجلسة (OTP عبر SMS/WhatsApp).
- البحث عن الأماكن عبر geocoding/POI.
- إنشاء/تحديث الرحلات ومسارات البديلة.
- إرسال/تأكيد/إبطال تنبيهات المجتمع.
- مشاركة الموقع الحي مع رابط.

## 5. تدفق البيانات الجغرافية
- **استيراد دوري لبيانات OSM:** منسّق ليلي مع فحص تعارض الأسماء وتصحيح الاتجاهات.
- **تصحيح محلي:** واجهة إشراف لقبول تعديلات المجتمع (POI، أسماء شوارع، اتجاهات).
- **حركة المرور الحية:** مزوّد خارجي + دمج بلاغات المجتمع مع وزن ثقة لمصادر متعددة.
- **تصحيح GPS:** استخدام Wi‑Fi positioning وA‑GNSS في المدن ذات التغطية الضعيفة.

## 6. العمل دون اتصال
- تنزيل بلاطات المدن/المحافظات مع تحديث تفاضلي صغير الحجم.
- تخزين مسارات الرحلات المتكررة محلياً، مع إعادة مزامنة عند الاتصال.
- تخزين صوتيات التوجيه وحزم اللغات محلياً.

## 7. الأمان والخصوصية
- جميع الاتصالات TLS 1.2+، وجلسات موقعة بـ JWT قصيرة العمر.
- مشاركة الموقع اختيارية ومؤقتة، مع طمس الإحداثيات في حالات الطوارئ.
- نظام سمعة للمبلّغين وحظر إساءة الاستخدام تلقائياً.

## 8. التطوير والاختبار
- **إدارة الإصدارات:** GitFlow مبسّط (main، develop، feature/*)، وإصدارات أسبوعية لـ beta.
- **الجودة:** اختبارات وحدات للمنطق، اختبارات تكامل لـ API، واختبارات UI آلية (Compose/SwiftUI + Detox/Flutter Driver).
- **CI/CD:** بناء أوتوماتيكي، فحص lint/format، وتحميل تجريبي إلى Firebase App Distribution/TestFlight.

## 9. خارطة الطريق التنفيذية (ملخص زمني)
- **الأسبوع 1–2:** إعداد البنية التحتية، تصميم مخطط البيانات، تنفيذ API للحساب/التوثيق.
- **الأسبوع 3–4:** دمج محرك المسارات، بناء شاشة الخريطة والبحث في التطبيق.
- **الأسبوع 5–6:** التنبيهات المجتمعية مع بث حي وتصويت، تحسينات حركة المرور.
- **الأسبوع 7–8:** الوضع دون اتصال، تحسين الأداء والقياسات، إطلاق نسخة Beta مغلقة.
- **ما بعد الإطلاق:** دعم الشاحنات والدراجات، طبقة حوادث الطقس، تحسين ML للتعرف على السرعة.

## 10. التالي المطلوب
- تأكيد اختيار التقنية (KMP vs Flutter) بناءً على فريق التطوير.
- تحديد مزود خرائط/حركة مرور رسمي وتراخيصه.
- بدء تنفيذ النواة: API الهوية + شاشة الخريطة + محرك التوجيه.
